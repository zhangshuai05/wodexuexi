## 4. c1 当前算法(v4)

核心:`c:\Users\EDY\Desktop\new\a2_v2.py`(418 行) / 嵌入版 `D:\...\diarization\claude_a2.py`

**主链路**:VAD 门控 → 1.2s/0.6s 滑窗 CAM++ 嵌入 → 跳变分段 → AHC 聚类(cosine, top-gap, link auto)→ 段标签

**分支一:auto 塌缩判据 + dense_rescue(我的 v3,保留)**
```python
collapsed = (n_switch <= 2 and 0.7 < dom_ratio < dom_max)   # dom_max=0.95
```
- `0.7 < dom < 0.95` → 真塌缩(两人被均值化揉成一团)→ 走 `_dense_rescue()`
- `dom >= 0.95` → 近单说话人(音频物理差/远场),不救(dense 也救不回,如 Call10836 密集窗仍塌 n1=437/n2=1)
- `_dense_rescue`:0.6s/0.15s 密集窗重提嵌入 → 距主导质心最远 30% 窗做远端种子 → 迭代 top-k 边距细化质心 → 逐窗 cos 判决 → 连续同标签窗切微段
- 救援失败(远端占比<10% 或两质心 cos>0.90)回退 window 聚类

**分支二:短答细化(Codex 的 v4 新增)** — `a2_v2.py:325-333`
```python
if (cluster_level == "segment" and len(set(labseq)) == 2
        and min(np.bincount(labseq)) >= 2):
    centroids = [reps[labseq == k].mean(axis=0) for k in (0, 1)]
    refined = _dense_rescue(x, sr, vsegs, spk_model, centroids=centroids)
```
- 普通**段级**路径也用短窗细化换人边界:复用段级两簇质心作身份参考,`_dense_rescue(centroids=...)`
  走特殊分支——保留调用方的说话人 ID,边界画在**相邻窗口中心之间**(避免重复音频、保留静音间隔)
- 门槛:每簇至少 2 个段级样本(孤立异常段不能当说话人参考)
- 效果:把被吞进长段的短应答("支付宝""哦""谢谢")拆出来。最长段从 14.4s/21.6s 降到 3.75s/3.9s

**分支三:`merge` 默认改为 `False`(Codex 修的 bug)**
- 旧前端 `merge=True` 与离线 `merge=False` 不一致,导致前端把多轮话拼成长段。现已统一 False。

## 10. 已知坑

1. **端口 8734 只能一个实例**。旧实例不死会抢端口 → 看起来"卡住"。
   `netstat -ano | grep 8734` 找 PID → `taskkill //F //PID <pid>` → 再起。
2. **首次请求模型冷启动 1~2 分钟**(VAD+CAM+++SEACO),cur 泳道密集短窗多,慢是正常。
3. **dense_rescue / 短答细化都要跑 0.6s 密集窗**,单文件 +10s 左右。用户说速度无所谓。
4. **prune_sliver > 0(碎段吸收)会掉分**——会把真实短应答("哦好""微信吧")吞掉,已弃用,保持 `0.0`。
5. **编码**:git bash 读中文文件名/内容会乱码,一律用 Python 以 `encoding='utf-8'` 读;
   `eval_detail.json` 用 GBK。**中文路径别用 Bash 传**,用 Read/Glob 工具(我曾因此误判文件不存在)。
6. **前端改动必须重启 web_server 才生效**。
7. **`merge` 前端/离线要一致**(现统一 False),否则前端会把多轮拼成长段——这是 v4 修掉的坑。
