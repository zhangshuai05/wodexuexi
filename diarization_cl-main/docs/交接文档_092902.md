## 2. ★ 三处静默失真（我自己发现，OCR 全都没报）

这三条是本轮**最有价值**的部分。共同形态：**不报错、只出错数**，
与本项目已确认的 bug 族完全同源。

### 2.1 ⚠️ `build_probe_cache` 无参数运行会把 manifest 从 12 场**覆盖成 3 场**

**而 `交接文档_0929.md` §11 的复现命令恰好是那条无参数的。**

根因：`--meetings` 的默认值是 `TARGET_MEETINGS`（第 2 步三场路径检查用的三场），
而 dev 12 场是**逐次累加**建出来的；`main()` 每次**新建** manifest 直接覆盖，
不合并既有场次。

**实测复现**（安全：`OUT` 改到临时目录，真 manifest 未被触碰）：

```
实际处理场次     : ['L_R003S01C02', 'L_R003S03C02', 'L_R003S04C02']
写入 manifest 数 : 3
真 manifest 场次 : 12 （未被本次运行触碰）
```

影响面**有界**：`probe_path_equiv.py:81` 的 `manifest_intervals` 只碰那 3 场，
不会 `KeyError`；但 manifest 会失真，另外 9 场的 VAD 区间记录丢失。

**修法**：`--meetings` 缺省改为「既有 manifest 的全部场次 ∪ `TARGET_MEETINGS`」，
写入时以既有条目为底再并入本次重建的。

**⚠️ 语义变了，必须知道**：现在**无参数 = 重建全部 12 场**（需加载模型、约 35 分钟）。
这**正好对上了 §11 注释里写的"重建 12 场"** —— 修复前那句话是错的，现在是对的。
只想重建三场的话，**必须显式传** `--meetings L_R003S01C02 L_R003S03C02 L_R003S04C02`。

### 2.2 `test_rescue_replacement.py` 的判据 6 是**恒真式**

```python
assert result["candidates"] is result["candidates"]   # 同对象取两次，恒 True
```

它对任何 payload 都成立，**断言不了**它注释声称的"candidates 也一并换成救援窗的"。
紧邻的判据（`max k >= 2`）也**照样恒真** —— 原因值得记住：

> **`_candidate_clusters` 对 k=2..10 一律生成候选，只是把不合格的标成
> `eligible: False`。** 所以主窗（单簇）那份候选表的 `max k` **恒为 10**。
> 单看 `max k` 区分不了两条路径的候选表。

**修法**：换成「存在 `k>=2` 且 `eligible`」——主窗单簇时**任何**划分都产生空簇、
必无合格候选；救援窗两簇均衡则 k=2 合格。判据因此真的指向"候选表已被替换"。

**反证**（注入「只换 `selected` 不换 `candidates`」，其余全对）：
精确变红，报出 `候选表里没有合格的 k>=2 —— candidates 仍是主窗（单簇）那份：
[(1, True), (2, False), (3, False), …]`，正好印出上面那个"`max k` 恒为 10"的结构。

### 2.3 `test_probe_cache_stages.py` 的"还原"没还原

末行 `importlib.reload(bpc)` 被当作还原，但它在 `monkeypatch` **仍生效时**执行 ——
reload 只是把 `STAGES` 用 `REFINE_MIN_VAD=0.123` **又重建一遍**。
实测跑完该测试后 `bpc.STAGES["refine"]["gate"]` 留在 **0.123**。

**修法**：`monkeypatch.undo()` **之后**再 reload，并加一条回归测试锁住
（`test_refine_gate_restored_after_monkeypatch`，紧跟其后、靠定义顺序看污染）。
**反证**：删掉 `monkeypatch.undo()` 即变红。

> 当前**无害**（后续无测试读 `STAGES`，唯一 import 它的
> `test_probe_silent_failures.py` 不读它），但顺序一变就会咬人。
