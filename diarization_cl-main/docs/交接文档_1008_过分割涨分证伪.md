## 1. 我们在做什么

项目：`C:\Users\EDY\Desktop\new`，AISHELL-4 单通道长会议（36–40 分钟）的
**说话人分离 + 段落 ASR**。生产入口 v12（`streaming_asr/claude_a2_v12.py`），
聚类组件来自 v11（`claude_a2_v11.py`）。

主指标：**句子级说话人归属率**（按句平均，弃权计入分母）。
另有两个**诊断口径**（这正是本轮的要点，见 §2）：

| 口径 | 定义 | 用途 |
|---|---|---|
| `oracle` | 每个预测簇**独立**取最常对应的真值人（**多对一**，现行主口径） | 上界 |
| `bijective` | 匈牙利**双射**：一个真值人只能被一个簇占用 | 诊断过分割代价 |
| `merged` | 先把 dup 簇并回该真值人的主簇，再按 `oracle` 打分 | 旁证（**区分力弱**，见 §3） |

## 2. 为什么这一轮是必要的（问题的由来）

上一轮（`docs/交接文档_0930b_大簇拆分.md`）留下一个**未解决的阻塞项**：

> 12 场的 oracle 峰值 k 是 `[7,6,7,6,5,10,8,6,5,8,6,5]`，**只有 1 场峰值是 10**；
> 但「恒选 k=10」的平均 regret 恰好是 **0.00**。这两件事只能同时成立，
> 如果 **oracle 准确率在大 k 上单调不减**。

机制确实存在且被写进了代码的 docstring（`probe_mapping_objective.score_oracle`）：

> 「过分割时两个簇同指一人，双射只能把真值给其中一个、另一个必然判错；
>  独立取最大则**两个都能对上**。」

⇒ **一个真人被切成 5 个簇，句级归属率不降。** 这就是「过分割不扣分」。

这一轮要回答的就是：**`k_all_best` 到底是真实收益，还是这个口径的产物？**

## 3. ★ 结论 ①：过分割涨分**一半成立**

新脚本 `scripts/evaluation/probe_over_seg_gain.py`。对 12 场取 **k=6 与 k=10** 两个
partition（上一轮 §4 指定的对照点），三个口径并排：

| 口径 | 均值 | 为正 |
|---|---:|---|
| Δoracle（多对一，现行） | **+0.97** pts | 5/12 |
| Δbijective（匈牙利双射） | **−2.52** pts | 2/12 |
| **Δmerged**（dup 并回主簇后） | **+0.67** pts | 4/12 |

**逐场分类（这是本轮的正式结论）：**

| 分类 | 场次 | 证据 |
|---|---|---|
| **真实拆分** | **4/12** | `L_R003S03C02` `M_R003S02C01` `M_R003S04C01` `S_R004S02C01` —— 合并 dup 后收益仍在 |
| **纯口径产物** | **1/12** | `L_R003S01C02` —— oracle 涨 +0.98，**合并后翻转成 −0.98** |
| **零收益／付代价** | **7/12** | Δoracle = 0.00，Δbijective 全负（−1.76 ~ −7.06） |

**最强的一条证据不在"涨分"，在"不涨分却受损"**：7 场的 Δoracle 恰好 `+0.00`
（多出的簇零信息增益），但双射口径下要付 −1.76 到 −7.06 点。
k=10 在 12 场**全**产出 10 个簇，而真值只有 5–6 人；其 `dup` 比例 30%–60%，12 场全 > 0。

**真实拆分的样板**（`M_R003S04C01`）：k=6 有个 240 窗的簇**混着 004-F 与 006-F**（纯度 59%），
k=10 拆成 167 窗的 004-F（83%）+ 62 窗的 006-F（**95%**）——真的把两个人分开了。
对比 `L_R003S01C02`：多出的簇主导人全是同一个已存在的说话人。
**同样"多 4 个簇"，性质完全相反。**

## 4. ★ 结论 ②：换尺子重跑消融表，「大 k 就好」塌了

新脚本 `scripts/evaluation/probe_rule_ruler.py`。**同一批规则、同一个候选表，只换尺子**：

| 规则 | oracle | bijective | merged |
|---|---:|---:|---:|
| prod（现行生产） | +12.99 | +12.46 | +12.87 |
| const_1 | +40.55 | +40.02 | +40.43 |
| const_2 | +23.03 | +22.61 | +22.91 |
| const_4 | +10.35 | +9.96 | +10.23 |
| **const_6** | +0.97 | **+1.05** ← 新最优 | +1.18 |
| **const_10** | **+0.00** | **+3.57** | +0.18 |
| four_criteria | +2.92 | +4.31 | +3.06 |
| no_gain（去掉 `gain>0`） | +2.92 | +4.31 | +3.06 |
| parent4_only | +0.09 | +2.99 | +0.28 |
| max_level_k | +0.09 | +2.99 | +0.28 |

**oracle 列逐行复现了上一轮 §2.2 / §2.3 的全部读数**（生产 k 与逐场 regret 也复现了），
所以这不是另一套口径算出的新数，是**同一批数字换了尺子**。

**三条结论：**

1. **`+0.00` 是尺子造的。** 恒选 k=10 在 oracle 下是 **12/12 场全 0.00**（完美得不真实）；
   换双射后 **10/12 场转正**，最差 `+8.00`（`S_R004S01C01`）。只有 2 场真的零 regret。
2. **上一轮那句推论被推翻。** 原文说「规则唯一的作用是剔掉 k=1/k=2，真正的信号是 k 越大越好」。
   新尺子下 `const_6`（+1.05）比 `const_10`（+3.57）便宜——**最优 k 是 ≈6，不是 10**。
   方向（该选更大）没变，**目标值变了**。
3. **但有一条原样保住**：`no_gain` 与 `four_criteria` **三列全部逐位相同**。
   「去掉 `gain>0` 结果完全不变」这件事换尺子后依然成立——**`gain` 作为判据确实失效**。

**两个口径各自的最优 k**：8/12 场相同；不同的 4 场里 oracle 的最优 k **一律不低于**
bijective，偏高 0–2。**11/12 场的生产 k 仍低于两口径的最优 k** —— **欠分割依旧是主因**。

## 8. 踩过的坑（**绝对不要再踩**）

### 坑 1：`.gitattributes` 的 `* text eol=lf` 会把二进制写坏（本会话最大的坑）

**症状**：`git status` 里长期有 180 个 `M`（png/xlsx/docx/pdf/wmf），
`git diff` 报 `Bin 705922 -> 705897 bytes`——**少了 25 字节，正好是 CRLF 的个数**。

**原因**：`.gitattributes` 只有一行 `* text eol=lf`，把**一切**当文本。
git 落盘时按 CRLF→LF 清洗，**直接破坏二进制**。

**危险性**：`git add` 会把损坏版**写进索引**（实测索引 blob 从 `4b217249` 变成 `ea99a5a2`）。
一次 `git add -A` 就能损坏 150 个 png。

**正确做法**：给二进制显式标 `-text`（本会话已修，18 类扩展名）。
**验证方法**（必做）：`git check-attr text -- x.png` 应输出 `text: unset`；
`git hash-object --path=x.png -- x.png` 应等于 `git rev-parse HEAD:x.png`。

**⚠️ 判断"文件是否真被改坏"的唯一可靠方法**是**逐字节 `cmp`**：
`git cat-file blob HEAD:<path> > /tmp/a && cmp /tmp/a <path>`。
**不要**用 `git status` 或 `git hash-object` 判断——它们受 eol filter 影响，会报假阳性。

### 坑 2：`git read-tree --empty` 会清空暂存区

想造一个"只含单文件"的临时提交来收窄 OCR 审查范围，用了
`git read-tree --empty` + `update-index --add --cacheinfo`。
后果：**暂存区被清空**，之前的归档改名全部变成未暂存；
随后的 `git reset --mixed HEAD` 又把这些改名彻底取消暂存。

**教训**：动索引的命令（`read-tree` / `reset` / `update-index`）**先确认工作区与暂存区
有没有未提交的重要状态**。要造临时提交，用 `GIT_INDEX_FILE` 指向**临时索引文件**，
完全不碰真实索引。

### 坑 3：`git status` 的 180 个 `M` 是假阳性

它们**不是**真的改动。磁盘内容与 HEAD **逐字节相同**，纯粹是 eol filter 的记账效果。
**千万不要**对它们跑 `git add -A`——那会把 150 个 png 真写坏（见坑 1）。
修 `.gitattributes` 后它们会自动消失（223 条 → 47 条）。

### 坑 4：`fcluster(maxclust)` 的簇数可能**少于** k（不会多于）

SciPy 语义是「**最多** t 个簇」。所以：
- 簇数 **< k** → `sizes = [... for l in range(k)]` 尾部补 0 → `min(sizes)=0` → 判不合格。
  **行为上合理**（保守拒绝）。
- 簇数 **> k** → **不可能**。所以「`range(k)` 漏掉尾部簇」这个 bug 不成立。

**但有个埋着的雷**：`sizes` 长度是 `k`，而 `_silhouette` 的 `groups` 来自
`sorted(set(labels))`，长度是**实际簇数 m**。m < k 时两者长度不一致——
现在因为不合格 → `score=-1.0` 而被掩盖。**一旦放宽 `eligible`（`unlocked_selector.py`
的 `core` 过滤正在做这件事），这个雷就会炸。**

### 坑 5：`_silhouette` 有一处潜在索引 bug

```python
own = labels[index]        # 簇标签"值"
other = min(... for label, group in enumerate(groups) ...)   # 簇的"序号"
```

`own` 用标签**值**去索引 `groups`，而 `label` 用的是**序号**。只在标签恰好是 `0..m-1`
时等价。而 `v12_aishell4.silhouette` 用的是 `group_of` 映射表——**两份实现不一致**，
而"生产 vs 基准"的可比性依赖它们一致。

### 坑 6：`_candidate_clusters` 的 `max_speakers` 是 `def` 时绑定的默认参数

`_v11_window_params` 改的是**模块变量** `v11.MAX_SPEAKERS`，
**改不动已经绑定的默认参数**。v12 必须在两处调用点**显式传参**。
回归：`tests/test_k_cap_dispatch.py` 必须报红。

### 坑 7：不要用 `git add -A`

long-standing 问题。`git status` 里长期混着**不属于本任务**的东西。
逐个精确暂存。

### 坑 8：读汇总列必须逐行核

**前几份交代替这条付出了三次代价**（`S_R004S01C01` 连续推翻作者两次）。
本轮的正面例子：Δoracle 均值 +0.97 看着像"大 k 有点用"，
但拆开是 **4 场真实 + 1 场假 + 7 场零收益**。

### 坑 9：`merge_dups` 前必须先 `classify_dup`

`merge_dups` 读 `is_dup` 字段。本会话初版传了全 `False` 的 dict，
**merged 列与 oracle 列逐位相同、静默失效**。
`probe_rule_ruler.py` 的 selfcheck 已加断言锁死：有 dup 的 k 上，
合并后簇数必须减少且 `merged != oracle`。
