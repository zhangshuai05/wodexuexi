## 1. 当前结论

**v7 是当前实际产品基线。v8、v9 都不能视为 v7 的升级版。**

**v7 和 v9 都需要经过 LLM 纠错后才有较好的最终体验。** LLM 纠错不是临时补救，
而是 PRD 流程图中“说话人分离之后”的正式处理阶段。算法评审既要单独检查 LLM 前
的声学分离能力，也必须以包含 LLM 的完整链路作为最终产品验收口径。

当前推荐组合是：

```text
Claude v7 + 自动 FRCRN 降噪 + DeepSeek LLM 校正
```

用户在真实音频 `dc7e27120023_04320.wav` 上试听并核对后，最终页面效果排序为：

```text
v7 + LLM > v9 + LLM > v8 原始结果
```

v8 页面结果的方法名没有 `+llm`，所以不能把该次 v7/v8 展示当作严格的同条件 LLM
对照；但同样经过 LLM 的 v7 与 v9 可以直接比较，v7 明显更好。v10 应从 v7
出发，不应继续在 v8/v9 上叠加修补。

## 2. 产品定位：会议系统，不是录音卡

v10 服务于**长时、多人、持续交互的会议系统**。文件上传和
`dc7e27120023_04320.wav` 只是当前开发测试入口，不是最终产品形态。不能把 v10
设计成“整段录音结束后再美化文本”的离线录音卡算法。

PRD 中的完整主链路应按下面理解：

```text
会议音频 -> 前端降噪 -> VAD/流式 ASR -> 说话人分离与身份跟踪
         -> LLM 纠错与轮次修订 -> 会议实时展示 -> 会后全局定稿
```

这带来以下硬要求：

- 会议进行中必须持续产生可见结果，不能等整场结束才输出。
- speaker 身份需要跨数十分钟保持连续，不能每个短块重新编号。
- LLM 纠错需要支持增量修订和会后定稿；不能每次重写全部历史，造成界面抖动。
- ASR 文本、speaker 时间线和 LLM 修订记录应分别保存，修订不能覆盖原始证据。
- 短答、连续换人、抢话、重叠发言和长时间连续讲话都是常态，不是边缘情况。
- 需要控制草稿延迟、端点修订延迟、推理 RTF、队列积压、显存和长时内存增长。
- 说话人数不能固定为两人。现有双人文件只能回归旧能力，不能作为多人会议验收集。
- 最终文本“读起来合理”不等于 speaker 和时间边界正确；LLM 生成的结构必须能回溯
  到声学证据，证据不足时应标记待确认。

因此 v10 需要同时设计在线路径和会后路径：在线路径重视稳定、低延迟和可修订；
会后路径允许利用全局上下文重新聚类和纠错，但必须保留 revision，并明确哪些结果
是在线草稿、端点修订和会后终稿。

## 5. 对评审结论的修正

评审结论中可以保留的部分：

1. `_stabilize_labels` 只消除 `A B A` 单窗翻转，不能消除连续两窗以上的短答。
2. `_absorb_slivers` 对双窗 run 不生效，因为其跨度正好是 `0.75s`。
3. 纯塌缩救援不传 `centroids`，因此不经过上述吸收逻辑。
4. v7 `_rescue_gate` 用欠切 window 的切换数约束 dense 候选，确实存在偏向少切的
   结构风险。04320 上也实测到 `13 > 4` 被拒绝。

不能保留的部分：

1. 04320 上 v8 没有放行 dense；它同样回退 window。
2. 旧页面显示 `00:06--00:06` 不能证明零长度段或 dense 路径。旧 `fmt()` 会把两端
   都向下取整。当前页面已改用十分之一秒显示。
3. 不能据此断言“唯一真凶是 v7 救援门”。当前 dense 候选本身有 13 次切换，且
   FRCRN 后 14 个 dense 段中有 8 个短于 `0.4s`，明显存在过切。

v8/v9 的静音支撑判据还包含一个短答冲突：

```text
pause >= 0.15s AND 相邻两段都 >= 0.75s
```

真实短答约 `0.5--0.7s`，即使边界落在静音上，也可能因 `min_run=0.75` 被标成
“无静音支撑”。这条判据不适合直接替换 v7 救援门。

## 6. v8、v9 为什么不再作为主线

### v8

- 23 文件可信子集平均 DER：v7 `18.1%`，v8 `20.0%`。
- 21/23 文件切换点不变，没有提高边界召回。
- 边界 precision/recall 都是 `83.8% / 33.1%`。
- 所谓人数 `23/23` 来自全部都是双人的现有语料，不能证明多人泛化。
- 外生门只诊断部分过切，对连续交接、抢话、重叠和短答不可靠。

### v9

- 修复了 ASR verdict、零切换救援和单人跨静音输出等契约问题。
- 没有修复边界 recall `33.1%` 的核心问题。
- 没有完成全量 23 文件效果复测。
- 04320 的 LLM 后结果仍把短问、回答和下一句合在同一说话人段中。

v8/v9 可以保留为诊断和失败案例，不应继续承担“新基线”的角色。

## 7. v10 的起点与硬约束

新对话开始设计 v10 时，先遵守以下约束：

1. **冻结 v7，不在 `claude_a2_v7_v8.py` 中原地改算法。**
2. 新建独立 v10 模块和 lane；先复制当前 v7 行为，再逐项做可关闭的实验。
3. v10 的对照基线必须是 `v7 + auto FRCRN + LLM`，而不是裸 v7。
4. v9 也必须完成 LLM 纠错后再做最终体验比较，不能拿 v9 raw 结果代表完整链路。
5. 同时保存并报告 LLM 前、LLM 后结果。不能用 raw 指标否定最终体验，也不能用
   LLM 后结果声称声纹分段算法已经切对。
6. 保留稳定的 `rescue_decision`、门限输入、候选段和最终采用路径诊断。
7. 不直接移植 v8/v9 的人数三态或 `unsupported_ratio <= 5%` 门。
8. 不使用 ZCA。现有全量诊断中 ZCA EER 为 `49.5%`，显著破坏可分性。
9. 不预设调阈值就能解决问题。此前 21/23 文件的切换点对门限变化不敏感。
10. 任何 v10 收益必须在冻结留出集上报告；04320 只能做回归样例，不能单独用于
   定阈值和宣称提升。
11. v10 必须面向会议流式处理设计；即使首个实验仍用文件回放，也必须限制模型只能
    读取已经回放到的音频，不能偷看后文后再声称达到实时效果。

建议 v10 优先回答的问题，而不是预设答案：

- 如何保留 v7 的稳定身份序列，同时让 `0.3--0.8s` 短答获得独立证据？
- dense 候选怎样限制连续噪声翻转，同时不拿欠切 window 当唯一裁判？
- LLM 为什么能在 v7 上恢复 8 个轮次，却在 v9 上仍合并短答？需要保存 LLM 输入、
  输出和提示词逐项比较。
- LLM 产生的新时间边界是否有声学依据？当前 v7+LLM 结果存在时间重叠，不能只因
  文本看起来合理就当作准确边界。

## 8. v10 最低验收口径

每个候选版本至少记录：

```text
输入音频哈希
降噪模式以及是否真的执行 FRCRN
VAD 配置哈希
算法版本和源码哈希
LLM 前 sentence_info + diag
LLM 请求和响应
LLM 后 sentence_info
人工标注对照
```

评测分成两层：

1. **算法层**：LLM 前 DER、边界召回、短答召回、碎段数、空解码和时间重叠。
2. **产品层**：LLM 后 speaker 归属、文字正确率、短答是否独立、时间边界是否合法。
3. **会议在线层**：首稿延迟、端点修订延迟、RTF、积压时长、身份漂移、重连后的
   revision 一致性，以及第 10--60 分钟内存增长。

04320 的回归要求至少包括：

- 自动降噪确实执行；
- “没有吗？”必须作为独立短答保留；
- 不能把“没有吗？对，然后……”归成同一人的一个长轮次；
- 不允许靠大量 `0.15s` 碎段通过；
- LLM 后若生成重叠时间段，必须标明其声学来源或判为待核验。

04320 只负责短答回归。v10 还必须使用至少一份真实多人长会议做调试，并用另一份
独立的 30--60 分钟会议做留出验收。人工标注至少包含：

```text
start_ms, end_ms, speaker_id, text, overlap
```

会议验收应覆盖暂停/恢复、长时间无停顿、尾块刷新、浏览器重连、模型异常、GPU
等待、处理积压和会后全局定稿。在线结果与会后结果分别报告，不能用会后修正后的
成绩冒充实时成绩。
